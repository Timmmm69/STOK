# Архитектура

Статус: нормативные правила инженерного harness. Этот документ описывает форму системы, а не разрешение реализовывать будущие продуктовые функции.

## Назначение

Проект строится как одно Next.js-приложение в одном Git-репозитории и одном npm-пакете. Архитектурный стиль — модульный монолит: доменные области изолированы внутри процесса и базы данных, но не разнесены по сервисам.

Текущий реализуемый срез ограничен технической проверкой `/health`, подключением к PostgreSQL, структурированным логированием и автоматическими проверками. Партии, товары, продажи, платежи, авторизация, аналитика, ИИ и SaaS-возможности в bootstrap не входят.

## Слои и направление зависимостей

Разрешённое направление зависимостей:

```text
Next.js UI / route handlers
            |
            v
application services / use cases
            |
            v
        domain model
            ^
            |
repositories and infrastructure adapters
            |
            v
 PostgreSQL / logging / external systems
```

- UI отвечает за отображение и пользовательское взаимодействие. Он не импортирует Prisma и не обращается к базе напрямую.
- Route handlers являются транспортными адаптерами: валидируют и преобразуют вход, вызывают application service, преобразуют результат в HTTP-ответ. Бизнес-логика в них запрещена.
- Application services координируют сценарий, транзакции и вызовы портов.
- Domain содержит правила и типы, не зависит от Next.js, Prisma или транспорта.
- Репозитории скрывают способ хранения данных. Prisma разрешён только в инфраструктурном слое.
- Внешние ошибки преобразуются в безопасные публичные ответы на границе системы; внутренние подробности остаются только в контролируемых логах.

## Модульные границы

Подготовлены границы будущих модулей:

`organizations`, `identity`, `suppliers`, `procurement`, `catalog`, `pricing`, `labeling`, `inventory`, `sales`, `payments`, `shifts`, `expenses`, `analytics`, `exceptions`, `audit`.

В bootstrap эти имена резервируют ответственность, но не дают разрешения создавать будущие сущности или сценарии «на всякий случай». Правила импорта и ответственности подробно описаны в [MODULE_BOUNDARIES.md](docs/architecture/MODULE_BOUNDARIES.md).

Каждый модуль должен иметь явный публичный контракт. Импорт внутренних файлов другого модуля, скрытая связь через общую таблицу и циклические зависимости запрещены. Общий код допустим только после появления как минимум двух доказанных применений и при отсутствии доменной принадлежности.

## Данные и транзакции

- PostgreSQL — основное хранилище, Prisma — единственная ORM.
- Уже применённые миграции неизменяемы; изменение схемы оформляется новой миграцией.
- В bootstrap допустимы только минимальные технические данные, необходимые для проверки инфраструктуры и детерминированного seed.
- Будущие бизнес-данные принадлежат организации и должны поддерживать `organization_id`.
- Значение `organization_id` нельзя доверенно принимать от клиента: сервер выводит доступную организацию из проверенного контекста прав.
- Деньги хранятся целыми числами в минимальных денежных единицах, не в `float`.
- Критические складские и финансовые изменения выполняются транзакционно.
- Повтор одного логического запроса не должен создавать дубли; механизм идемпотентности выбирается для конкретного сценария.
- Исправления финансовых и складских фактов оформляются обратными или корректирующими операциями, а не бесследным удалением.

Текущие и будущие ограничения данных описаны в [DATA_MODEL.md](docs/architecture/DATA_MODEL.md).

## Health-срез

Технический health endpoint проверяет приложение и базу независимо. Успешный ответ имеет HTTP `200`, недоступная база — `503`. Ответ структурирован, содержит временную метку и не раскрывает строку подключения, секреты или внутреннее сообщение ошибки. Проверка базы ограничена по времени.

Страница `/health` — единственный разрешённый пользовательский экран bootstrap; она показывает состояние инфраструктуры и не является продуктовым интерфейсом.

## Сквозные требования

- Все входы считаются недоверенными и валидируются на серверной границе.
- Логи структурированы; секреты и персональные данные в них запрещены.
- Ошибка внешней зависимости должна завершаться явно и наблюдаемо, без ложного успешного ответа.
- Архитектурные границы и циклы проверяются автоматически.
- Решение о новой зависимости, новой абстракции или пересечении модулей должно иметь конкретное текущее основание.

## Зафиксированный исходный стек

- Node.js 24.14.0, pnpm 11.9.0, TypeScript 6.0.3;
- Next.js 16 / React 19 App Router как один UI и server runtime;
- PostgreSQL 18.4 и Prisma 7 с обязательным `@prisma/adapter-pg`;
- Zod на недоверенных входах, Pino для структурированных логов;
- Vitest для unit/integration, Playwright для браузерного smoke;
- Docker Compose локально и GitHub Actions в CI.

Версии фиксируются `package.json`, lock-файлом, `.node-version`, CI и runbook. Смена ключевой технологии требует ADR.

## Изменение архитектуры

Существенное отклонение от утверждённого стека, модульного монолита, одного приложения или правил владения данными сначала оформляется ADR и добавляется в [индекс решений](docs/decisions/index.md). Документация и автоматические проверки меняются в том же вертикальном срезе, что и код.
