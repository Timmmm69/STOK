# Исходная концепция продукта v1

Статус: исторический исходный материал, переданный владельцем продукта 2026-07-18. Текст ниже сохранён без смыслового сокращения; нормативные решения находятся в `docs/product/`.

## 5.1. Определение продукта

Создаётся специализированная система операционного и управленческого учёта для небольших магазинов с большим количеством уникальных товаров.

Первая вертикаль — небольшие секонд-хенды, которые:

- закупают одежду партиями по весу;
- не получают готового поштучного каталога;
- вручную сортируют вещи;
- вручную назначают цены;
- используют обычные физические ценники;
- не имеют достоверного учёта каждой вещи;
- принимают оплату наличными или через отдельный банковский терминал;
- хотят понимать остатки, продажи, расходы и результаты закупок;
- не хотят тратить много времени на ручное заполнение карточек.

Исходный собственный магазин:

- один магазин;
- около 300 кг товара;
- примерно 15 проданных вещей в день;
- товар закупается партиями по весу;
- точная закупочная себестоимость отдельной вещи неизвестна;
- отдельного товарного учёта пока нет;
- инвентаризация не проводилась;
- обслуживание системы желательно удерживать примерно в пределах 30 долларов в месяц без учёта оборудования.

Продукт сначала создаётся для собственного магазина.

После проверки он должен развиваться:

1. В систему для других секонд-хендов.
2. В SaaS для нескольких организаций и магазинов.
3. В систему для близких форматов:

   - винтажных магазинов;
   - магазинов уникальных вещей;
   - комиссионных магазинов;
   - аутлетов;
   - шоурумов.

4. Позднее — в отдельные продуктовые слои для обычной розницы.

Не нужно сразу создавать универсальную ERP для любого бизнеса.

## 5.2. Основная проблема

Главная проблема не в отсутствии графиков.

Главная проблема заключается в отсутствии достоверной связи между:

- физической вещью;
- закупочной партией;
- назначенной ценой;
- продажей;
- оплатой;
- остатком;
- возвратом;
- списанием;
- управленческим решением.

Без этой связи аналитика создаёт видимость точности.

Основная ценность продукта:

> Быстро поставить на учёт большое количество уникальных вещей, не потерять остатки и понять, какие закупки возвращают деньги.

Штрихкод — не самостоятельная ценность, а дешёвый механизм связи физической вещи и цифровой записи.

## 5.3. Проблемы, которые должен решать продукт

### Товар

- неизвестно точное количество вещей;
- нельзя определить, какая вещь продана;
- невозможно провести надёжную инвентаризацию;
- старый и новый товар смешиваются;
- партии смешиваются;
- повреждённые, потерянные и проданные вещи остаются в фиктивном остатке;
- история изменения цены отсутствует.

### Продажи

- продавец вручную складывает цены;
- несколько вещей легко пропустить;
- одну вещь можно случайно учесть дважды;
- сумма отдельно вводится в банковский терминал;
- система и терминал могут расходиться;
- скидки и возвраты могут проходить вне учёта;
- состав продажи неизвестен.

### Финансы

- выручка смешивается с прибылью;
- закупка партии не связывается с её продажами;
- расходы фиксируются нерегулярно;
- точная себестоимость отдельной вещи неизвестна;
- непонятно, окупилась ли партия;
- непонятно, сколько денег вложено в остаток.

### Управление

- закупки совершаются интуитивно;
- уценка проводится без проверки результата;
- неизвестно, какие категории действительно продаются быстрее;
- абсолютные продажи категорий не нормализуются по доступному остатку;
- нельзя надёжно сравнивать партии разного возраста;
- невозможно проверить, помогло ли управленческое решение.

## 5.4. Пользователи

### Собственник

Хочет:

- понимать продажи и прибыль;
- контролировать магазин без постоянного присутствия;
- видеть расхождения;
- понимать результат партий;
- уменьшать залежавшийся товар;
- принимать решения по закупкам и ценам;
- не вести сложный ручной учёт.

### Продавец

Хочет:

- быстро обслуживать покупателей;
- не считать сумму вручную;
- быстро исправлять ошибки;
- не задерживать очередь;
- легко закрывать смену;
- не заполнять длинные формы.

### Сотрудник приёмки

Хочет:

- быстро разобрать партию;
- сначала работать физически, а не постоянно смотреть в экран;
- массово создавать товары;
- массово печатать ценники;
- не заполнять бренд, цвет, материал и описание каждой вещи.

На старте один человек может совмещать несколько ролей.

---

## 5.5. Основные продуктовые принципы

### Минимальный обязательный ввод

Для обычной вещи достаточно:

- партии;
- категории;
- цены.

Количество вводится один раз для физически сформированной группы.

Система автоматически создаёт:

- отдельные товарные единицы;
- уникальные идентификаторы;
- короткие номера;
- штрихкоды;
- даты;
- статусы;
- историю операций.

### Массовая обработка

Пользователь не должен вручную создавать 20 одинаковых карточек.

Пример:

> Партия №15 → женский верх → 25 BYN → 20 вещей.

Система создаёт 20 отдельных товарных единиц.

### Детальный режим только при необходимости

Для дорогого или онлайн-товара позднее можно добавить:

- фото;
- бренд;
- размер;
- состояние;
- описание;
- индивидуальную цену.

Детальный режим не должен замедлять основной процесс.

### Неизменяемая история

Продажи, платежи, возвраты, списания и критические финансовые операции нельзя бесследно удалять.

Ошибки исправляются отдельными корректирующими операциями.

### Код считает факты

Обычный программный код рассчитывает:

- продажи;
- остатки;
- себестоимость;
- прибыль;
- проценты;
- сроки;
- расхождения.

ИИ не является источником истины.

### Специализированный интерфейс и нейтральное ядро

Интерфейс первой версии использует понятные слова:

- партия;
- вещь;
- цена;
- продано;
- возврат;
- уценка.

Внутренняя модель не должна быть жёстко привязана только к мешкам одежды.

## 5.6. Основные сущности

Нужно концептуально разделять:

### Товарная модель

Описание типа товара.

В первой версии может содержать только категорию.

Позднее может содержать:

- название;
- бренд;
- артикул;
- свойства;
- варианты.

### Товарная группа

Группа массового создания:

- партия;
- категория;
- цена;
- количество.

### Физическая товарная единица

Конкретная вещь:

- уникальный ID;
- внутренний штрихкод;
- короткий номер;
- партия;
- группа;
- текущая цена;
- статус;
- локация;
- дата выставления;
- история.

В будущем ядро должно быть способно поддержать:

- уникальные товарные единицы;
- одинаковые SKU с количественным остатком;
- партии или лоты с количеством.

Не нужно реализовывать все три модели сейчас.

## 5.7. Путь товара

### 1. Создание партии

Собственник вводит:

- поставщика;
- вес;
- стоимость закупки;
- доставку;
- известные прямые расходы;
- дату;
- комментарий.

Количество вещей заранее неизвестно.

Партия создаётся как черновик со статусом «В обработке».

### 2. Физическая сортировка

Сотрудник:

- открывает партию;
- проверяет вещи;
- отделяет брак;
- сортирует по категориям;
- делит внутри категории по ценам.

Во время физической сортировки система не должна требовать постоянной работы с экраном.

### 3. Создание товарной группы

Пользователь выбирает:

- партию;
- категорию;
- цену;
- количество.

Система показывает предпросмотр и после подтверждения массово создаёт отдельные товарные единицы.

Повторное нажатие не должно создавать дубли.

### 4. Печать ценников

Ценник содержит:

- крупную цену;
- краткую категорию;
- штрихкод;
- короткий читаемый номер.

Система хранит:

- задание печати;
- диапазон;
- пользователя;
- дату;
- историю перепечаток.

Перепечатка не создаёт новый товар.

Должна быть возможна допечатка выбранного диапазона.

### 5. Сверка маркировки

После прикрепления ценников сотрудник указывает:

- фактически промаркированное количество;
- испорченные ценники;
- лишние ценники.

Группа не должна незаметно закрываться при расхождении количества.

### 6. Активация

После сверки группа становится доступной к продаже.

Повторное сканирование каждой вещи при размещении в зале для первой версии не требуется.

### 7. Источник истины цены

Физический ценник и активная цена в системе должны совпадать.

Изменение цены:

1. Создаёт новую цену в состоянии ожидания.
2. Создаёт задание на новый ценник.
3. Требует физической замены.
4. Активируется после подтверждения замены.

До подтверждения действует старая цена.

## 5.8. Продажа

### Открытие смены

Продавец:

- открывает смену;
- вводит наличные на начало;
- видит незавершённые операции.

### Сканирование

После сканирования система:

- находит вещь;
- проверяет статус;
- добавляет в корзину;
- показывает цену;
- увеличивает крупный счётчик;
- воспроизводит понятный сигнал.

Повторный скан одной вещи блокируется.

### Несколько вещей

На экране постоянно видны:

- количество вещей;
- состав корзины;
- цена каждой вещи;
- итоговая сумма.

### Нечитаемый код

Последовательность восстановления:

1. Ввести короткий номер.
2. Использовать камеру.
3. Найти по ограниченным признакам.
4. Провести продажу без идентификации как исключение.

Продажа не должна блокироваться, но исключение обязательно попадает владельцу на проверку.

### Скидка, уценка и акция

Это разные операции.

- Скидка — разовое снижение цены в конкретной продаже.
- Уценка — постоянное изменение цены товара.
- Акция — временное правило для группы.

Продавец имеет ограниченный лимит скидки.

---

## 5.9. Оплата

### Наличные

Продавец:

- выбирает наличные;
- при необходимости вводит полученную сумму;
- получает расчёт сдачи;
- подтверждает оплату.

### Карта через отдельный терминал

Корзина переводится в состояние ожидания оплаты.

Товар не списывается до результата терминала.

Продавец выбирает:

- одобрено;
- отклонено;
- повторить;
- изменить способ;
- отменить чек.

Только после подтверждения «Одобрено»:

- создаётся продажа;
- создаётся платёж;
- товары получают статус «Продано»;
- обновляется остаток.

Незавершённая карточная оплата должна оставаться явно видимой.

### Атомарность

Завершение продажи должно одной транзакцией:

- создать продажу;
- создать позиции;
- создать платёж;
- изменить статусы товаров;
- обновить остаток;
- записать выручку.

Не допускается частично сохранённая продажа.

---

## 5.10. Исключения и корректировки

Нужен единый центр:

> Требует внимания.

Туда попадают:

- продажа без кода;
- незавершённая оплата;
- расхождение смены;
- потерянный ценник;
- лишняя этикетка;
- неподтверждённая группа;
- ручная цена;
- товар без категории;
- не найденный товар;
- несинхронизированная операция;
- необычная скидка;
- повторные перепечатки.

Каждое исключение должно содержать:

- проблему;
- возможное последствие;
- ответственное лицо;
- рекомендуемое действие.

### Возврат

Возврат выполняется по конкретной позиции исходной продажи.

### Отмена

Исходная продажа не удаляется. Создаётся отменяющая операция.

### Списание

Фиксируются:

- товар;
- причина;
- пользователь;
- время.

### Восстановление

Если товар найден, создаётся операция восстановления. История не исчезает.

## 5.11. Закрытие смены

Продавец вводит:

- фактические наличные;
- итог терминала.

Система показывает:

- ожидаемые наличные;
- фактические наличные;
- расхождение;
- ожидаемую сумму карты;
- сумму терминала;
- расхождение;
- возвраты;
- отмены;
- скидки;
- незавершённые операции;
- продажи без кода.

Расхождения нельзя скрыть удалением.

---

## 5.12. Себестоимость

Точная себестоимость отдельной вещи неизвестна.

Метод первой версии:

> Полная стоимость партии ÷ количество продаваемых единиц.

Полная стоимость включает:

- закупку;
- доставку;
- прямые дополнительные расходы.

Показатель всегда называется:

> Расчётная себестоимость.

На уровне партии можно показывать:

- стоимость;
- выручку;
- расчётную прибыль;
- возврат вложений;
- срок окупаемости.

На уровне категории в первой версии надёжнее показывать:

- продажи;
- выручку;
- скорость;
- остаток;
- возраст;
- распродаваемость.

Не следует выдавать категорийную прибыль за точную.

Метод себестоимости должен иметь версию. Старые отчёты нельзя незаметно пересчитывать новой формулой.

## 5.13. Аналитика

### Главный экран

- выручка;
- проданные вещи;
- чеки;
- средний чек;
- наличные;
- карта;
- расчётная валовая прибыль;
- проблемы, требующие внимания.

### Продажи

- чистая выручка;
- чеки;
- вещи;
- средний чек;
- средняя цена вещи;
- вещей в чеке;
- продажи по дням;
- категории;
- ценовые диапазоны;
- скидки;
- возвраты;
- способы оплаты.

### Товар

- остаток;
- расчётная стоимость;
- розничная стоимость;
- возраст;
- товар без движения;
- уценённый товар;
- списания;
- недостачи.

### Партии

- стоимость;
- вес;
- количество вещей;
- выход вещей на килограмм;
- доля брака;
- продано;
- остаток;
- выручка;
- возврат вложений;
- дата окупаемости;
- выручка на килограмм;
- расчётная прибыль на килограмм;
- возраст.

Партии сравниваются на одинаковом возрасте:

- первые 7 дней;
- первые 14 дней;
- первые 30 дней.

### Категории

- получено;
- продано;
- остаток;
- выручка;
- средняя цена;
- медианный срок продажи;
- скорость продаж относительно доступного остатка;
- возраст;
- доля залежавшегося товара;
- доля продаж после уценки.

Не нужен один искусственный рейтинг категорий.

Нужна матрица решений:

- быстро продаётся, низкий остаток;
- быстро продаётся, высокий остаток;
- медленно продаётся, новый товар;
- медленно продаётся, старый товар.

### Финансы

Нужно разделять:

- валовую прибыль;
- операционную прибыль;
- движение денег.

Система не является полноценной бухгалтерией.

Не следует показывать «свободные деньги», пока не учитываются обязательства, налоги и будущие платежи.

## 5.14. Качество данных

Любой аналитический отчёт должен показывать степень доверия.

Индикаторы:

- доля продаж через сканирование;
- продажи без кода;
- незакрытые смены;
- незавершённые платежи;
- неподтверждённые группы;
- товары без категории;
- дата последней инвентаризации;
- полнота расходов;
- кассовые расхождения;
- несинхронизированные операции.

Уровни доверия:

- недостаточно данных;
- предварительный сигнал;
- данные пригодны для решения;
- высокий уровень доверия.

---

## 5.15. Управленческие решения

Система должна хранить решения владельца:

- тип решения;
- выбранные товары;
- дата;
- причина;
- старая цена;
- новая цена;
- целевая метрика;
- ожидаемый эффект;
- дата проверки.

После контрольного периода система сравнивает результат до и после.

Нельзя автоматически считать совпадение доказанной причинностью.

---

## 5.16. ИИ

### Стадия 1

Ручной экспорт агрегированных данных в ChatGPT.

### Стадия 2

Автоматический недельный отчёт через API.

### Стадия 3

Встроенный аналитический помощник.

### Стадия 4

Помощник предлагает действия, но применяет их только после подтверждения владельца.

Программный код рассчитывает цифры.

ИИ:

- объясняет;
- формирует гипотезы;
- предлагает действия;
- отвечает на вопросы по рассчитанным данным.

ИИ не должен самостоятельно:

- пересчитывать источник истины;
- менять цены;
- проводить продажи;
- списывать товары;
- отменять операции;
- создавать расходы;
- обвинять сотрудника;
- определять факт кражи.

ИИ не входит в первый пилот.

---

## 5.17. Инвентаризация

Два режима:

### Полная

Сканируется весь магазин.

### Циклическая

Проверяется:

- категория;
- партия;
- зона;
- дорогие товары;
- рискованные товары;
- случайная выборка.

Статусы расхождения:

- найден;
- не найден;
- найден лишний;
- проданный товар найден;
- требуется повторная проверка;
- подтверждена недостача;
- восстановлен.

Недостача не равна доказанной краже.

---

## 5.18. Перенос текущего остатка

Не нужно заранее принуждать магазин к полной одномоментной маркировке всех 300 кг.

Варианты:

1. Полный перенос.
2. Учёт только новых партий.
3. Поэтапный перенос.

Предпочтительная гипотеза:

- новые партии учитываются полностью;
- дорогой и новый старый товар маркируется первым;
- остальной остаток переносится категориями;
- исторический товар помечается отдельно;
- аналитика показывает долю полностью учтённого остатка.

Окончательное решение принимается после пилота.

---

## 5.19. Полевой пилот

До полной разработки нужно проверить основную гипотезу:

> Индивидуальный учёт вещей создаёт достаточную ценность и не вызывает неприемлемой дополнительной работы.

Пилот:

- одна партия;
- 50–100 вещей;
- 5–10 категорий;
- несколько цен;
- реальный принтер;
- реальный сканер;
- 3–5 рабочих дней;
- один продавец;
- один сотрудник приёмки.

В пилот входят:

- партия;
- групповое создание;
- штрихкоды;
- печать;
- допечатка;
- сверка;
- корзина;
- наличные;
- карта;
- короткий номер;
- продажа без кода как исключение;
- простой остаток;
- закрытие смены;
- журнал операций.

В пилот не входят:

- глубокая финансовая аналитика;
- ИИ;
- несколько магазинов;
- SaaS-биллинг;
- прогнозы;
- сложные рейтинги;
- полноценный офлайн;
- онлайн-продажи.

Метрики пилота:

- время старого процесса;
- время нового процесса;
- дополнительное время на 100 вещей;
- стоимость дополнительного труда;
- ошибки количества;
- лишние ценники;
- перепечатки;
- ошибки связи;
- доля продаж через систему;
- время продажи;
- пропущенные сканы;
- дубли;
- расхождения терминала;
- расхождения наличных;
- восстановление потерянного кода;
- попытки обхода системы.

Предварительные критерии успеха:

- не менее 98% товаров корректно учтены;
- не менее 98% продаж проходят через систему;
- нет дублей из-за повторного запроса;
- продажа одной вещи занимает до 8 секунд без терминала;
- продажа пяти вещей занимает до 25 секунд без терминала;
- терминал и система сходятся;
- потерянный код не блокирует продажу;
- сотрудники работают без разработчика;
- дополнительное время обработки приемлемо;
- владелец принимает хотя бы одно решение на основе данных.

Причины пересмотреть концепцию:

- маркировка увеличивает время более чем в два раза;
- продавец регулярно обходит сканирование;
- ценники часто перемешиваются;
- терминал постоянно расходится с системой;
- аналитика не используется;
- расходы превышают доказанную пользу.

## 5.20. Масштабирование

Сразу концептуально предусмотреть:

- организации;
- магазины;
- локации;
- роли;
- настраиваемые категории;
- валюту;
- канал продажи;
- историю цены;
- историю статуса;
- метод себестоимости;
- уникальные ID операций;
- изоляцию данных;
- экспорт;
- тарифные разрешения.

Не нужно сразу создавать интерфейсы для:

- нескольких организаций;
- нескольких магазинов;
- складов;
- сложных ролей;
- биллинга;
- международных налогов;
- всех возможных атрибутов.

Последовательность развития:

1. Полевой пилот.
2. Операционный MVP.
3. Управленческий MVP.
4. ИИ-аналитика.
5. SaaS для секонд-хендов.
6. Вертикальные модули для соседних форматов.
7. Отдельный слой обычной розницы.

---

## 5.21. Экономическая гипотеза

До масштабирования нужно измерять:

### Расходы

- дополнительный труд;
- этикетки;
- оборудование;
- сервер;
- база;
- резервные копии;
- поддержка;
- ИИ позднее.

### Пользу

- уменьшение недостач;
- уменьшение кассовых ошибок;
- экономию времени;
- улучшение закупок;
- эффект уценки;
- уменьшение залежавшегося товара;
- контроль скидок.

Экономический эффект:

> предотвращённые потери
>
> - дополнительная прибыль
> - экономия времени
>   − дополнительный труд
>   − расходники
>   − оборудование
>   − стоимость сервиса.

Эта формула пока является гипотезой и должна быть проверена полевыми данными.
