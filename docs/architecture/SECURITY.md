# Безопасность

Статус: baseline инженерного harness. Полноценная авторизация и SaaS-изоляция ещё не реализованы.

## Текущая поверхность

Bootstrap публикует только технические страницы и health endpoint. Health-ответ сообщает состояние приложения и базы, но не возвращает строку подключения, секрет, SQL, stack trace или внутреннее сообщение исключения. Подробность диагностируется по серверному структурированному логу.

Наличие health endpoint не является проверкой доступа и не доказывает готовность продуктовой авторизации.

До реализации проверенного входа публично допустимы только технический health и экран входа. Настройка организации, товары, продажи и любые непубличные данные не могут быть размещены в интернете за «секретной ссылкой» или одним клиентским скрытием интерфейса.

## Границы доверия

- Любые HTTP-данные недоверенны и валидируются на сервере, при необходимости через Zod.
- UI не является границей авторизации.
- Route handler не обращается к Prisma и не принимает решения по бизнес-правам самостоятельно.
- Ошибка внутреннего сервиса преобразуется в ограниченный публичный ответ.
- Логи, trace и тестовые артефакты рассматриваются как потенциально чувствительные данные.

## Будущая изоляция организаций

Каждая бизнес-сущность клиента должна иметь `organization_id`. Организация и права выводятся из проверенного серверного identity-контекста. Переданный клиентом `organization_id` можно использовать только как заявленный параметр, который обязан совпасть с разрешённой областью; сам параметр не предоставляет доступ.

Репозитории должны требовать серверный контекст организации и применять его ко всем чтениям и изменениям. Составные уникальные ограничения и индексы учитывают организацию там, где уникальность локальна для арендатора. Перед выпуском SaaS-режима нужны отдельные негативные тесты межорганизационного доступа.

## Секреты и конфигурация

- Репозиторий содержит только `.env.example` с безопасными локальными значениями или placeholders.
- `.env` и варианты с реальными значениями игнорируются Git и проверяются сканером секретов.
- Секреты не встраиваются в клиентский bundle, логи, сообщения ошибок, снимки и test fixtures.
- CI pull request использует локальный PostgreSQL service и не требует производственных секретов.
- Производственные секреты в будущем поступают из управляемого хранилища окружения и регулярно ротируются.

## Логирование и данные

Структурированный лог допускает технический correlation/idempotency identifier, код события, уровень, длительность и безопасный контекст. Пароли, токены, строки подключения, платёжные реквизиты, полное тело запроса и персональные данные в логах запрещены. Неизвестные исключения логируются через безопасную нормализацию и не отражаются клиенту дословно.

## Зависимости и поставка

- Версии среды и зависимостей зафиксированы lock-файлом и CI.
- Зависимость добавляется только с объяснением необходимости и оценкой поддержки/риска.
- Проверки форматирования, типов, архитектуры и тестов нельзя обходить или отключать.
- Сгенерированные артефакты и миграции просматриваются в diff перед слиянием.

## До первого интернет-среза

- Выбрать поддерживаемый способ входа и политику сессий.
- Создать единственного приглашённого владельца без свободной регистрации.
- Защитить каждый непубличный серверный маршрут и проверить отказ без сессии.
- Определять организацию на сервере через членство пользователя, а не через параметр браузера.
- Утвердить домен, HTTPS, хранение секретов и минимальный порядок восстановления.
