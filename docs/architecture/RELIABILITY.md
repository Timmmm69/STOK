# Надёжность

Статус: baseline для локального harness; целевые SLO продукта ещё не определены.

## Health contract

Health endpoint независимо отражает приложение и PostgreSQL:

- HTTP `200`, `status: "ok"`, когда приложение и база доступны;
- HTTP `503`, безопасный degraded-статус, когда база недоступна или проверка превысила лимит;
- структурированный JSON с `checks.application`, `checks.database` и ISO-временной меткой;
- никакой строки подключения, секрета, SQL, stack trace или внутренней ошибки в ответе.

Проверка базы имеет единый короткий timeout для ответа приложения, подключения драйвера и SQL-запроса, поэтому операция не должна продолжаться после истечения лимита. Ошибка логируется структурированно с безопасным техническим контекстом. Контракт покрывается unit/HTTP-тестами успеха и недоступной базы, интеграционным тестом PostgreSQL и e2e smoke-тестом страницы.

## Отказы и наблюдаемость

- Зависимость не маскирует отказ успешным ответом.
- Сообщение клиенту стабильно и безопасно; диагностическая причина остаётся на сервере.
- Логи содержат timestamp, уровень, код события и полезный неперсональный контекст.
- Известные ошибки отделяются от неизвестных; неизвестные не проглатываются.
- Произвольные задержки в тестах запрещены, если можно ждать наблюдаемое состояние.

## Данные

- Изменения схемы выполняются миграциями; опубликованные миграции неизменяемы.
- Seed и fixtures детерминированы.
- Локальная и тестовая базы изолированы.
- Резервная копия считается полезной только после успешной проверки восстановления.
- Порядок локального восстановления и будущие production-требования описаны в [DATABASE_RECOVERY.md](../runbooks/DATABASE_RECOVERY.md).

## Будущие критические операции

До реализации каждого финансового или складского сценария нужно определить:

- атомарную транзакционную границу;
- idempotency key и срок его действия;
- уникальные ограничения против дублей;
- конкурентные конфликты и стратегию retry;
- компенсирующую операцию вместо бесследного удаления;
- аудит, reconciliation и ручное восстановление.

Retry допустим только для классифицированной временной ошибки, ограничен числом попыток и не нарушает идемпотентность. Неопределённый бесконечный retry запрещён.

## Резервирование и восстановление

Для production до запуска должны быть утверждены владельцы, расписание, шифрование, срок хранения, RPO/RTO и регулярный restore drill. Bootstrap не настраивает платный внешний backup-сервис и не создаёт видимость производственной готовности.
