# Границы модулей

Статус: обязательные правила модульного монолита.

## Карта

Будущие доменные модули: `organizations`, `identity`, `suppliers`, `procurement`, `catalog`, `pricing`, `labeling`, `inventory`, `sales`, `payments`, `shifts`, `expenses`, `analytics`, `exceptions`, `audit`.

Bootstrap создаёт только структуру границ. Пустая граница не должна содержать доменные сущности, таблицы, API или заготовленные use cases.

## Внутренняя форма модуля

Когда у модуля появится подтверждённый вертикальный срез, код разделяется по ответственности:

- `domain` — типы, правила и порты без зависимостей на Next.js и Prisma;
- `application` — use cases и координация транзакций;
- `infrastructure` — реализации репозиториев и внешних адаптеров;
- публичная точка входа — минимальный контракт для разрешённых потребителей.

Каталоги создаются по мере реальной необходимости. Не нужно создавать слой или абстракцию, у которых только одно гипотетическое будущее применение.

## Разрешённые зависимости

- Next.js UI и route handlers могут импортировать публичный application-контракт нужного модуля.
- Application может использовать собственный domain и объявленные порты.
- Infrastructure реализует порты своего модуля и может зависеть от Prisma/логирования.
- Межмодульный вызов идёт только через публичную точку входа владельца.
- Нейтральная инфраструктура может предоставлять технические адаптеры, но не становится местом общей бизнес-логики.

## Запрещённые зависимости

- Prisma Client или база данных из UI.
- Prisma Client или прямой запрос к базе из route handler.
- Бизнес-правила в React-компоненте, Server Component или route handler.
- Импорт внутреннего файла другого модуля.
- Чтение или изменение таблицы другого модуля в обход его контракта.
- Циклическая зависимость любого уровня.
- Скрытая связь через глобальное изменяемое состояние, неявный singleton или недокументированный side effect.
- Общий `utils`-слой для кода с доменной ответственностью.

## Взаимодействие

Синхронный вызов внутри процесса является исходным вариантом. Событие или очередь добавляются только при подтверждённой необходимости в асинхронности, согласованности или изоляции отказов. Kafka, микросервисы и отдельное аналитическое хранилище в текущую архитектуру не входят.

Если один use case затрагивает несколько модулей, до реализации фиксируются:

- владелец orchestration;
- публичные контракты участников;
- транзакционная граница;
- поведение при частичном отказе и повторе;
- данные аудита.

## Автоматическая защита

Архитектурная проверка должна завершаться ошибкой при цикле, запрещённом межмодульном deep import и импорте Prisma из UI/route handlers. Линтер или правило нельзя отключать ради зелёного результата; исключение возможно только как документированное архитектурное решение с более узкой автоматической защитой.

## Проверка изменения

Перед изменением соседнего модуля автор объясняет, почему публичного контракта недостаточно. Новый shared-код требует как минимум двух текущих использований. Любое изменение границы обновляет этот документ, соответствующий ADR и тесты в том же срезе.
